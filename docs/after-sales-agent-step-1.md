# 电商售后 Agent：第一步业务规则

## 1. 目标和边界

本项目实现一个面向已登录用户的电商售后 Agent。它可以查询用户自己的订单、解释规则、引导用户提交售后申请，并在需要时自动创建人工工单。

第一版不直接执行真实退款、真实物流查询或真实短信通知：

- 退款和退货均创建售后申请，由后台管理员审核。
- 订单只有待支付、已支付、已取消、已发货四种状态，不伪造“已签收”或快递轨迹。
- Agent 只能调用服务端预先注册的工具，不能执行 SQL、Shell、文件操作或任意 HTTP 请求。

## 2. 用户可处理的问题

| 意图 | 典型表达 | Agent 行为 | 是否自动建工单 |
| --- | --- | --- | --- |
| 订单查询 | “我的订单在哪”“我买了什么” | 查询当前用户的订单 | 否 |
| 订单详情 | “看一下这个订单” | 查询订单商品、金额、状态 | 否 |
| 物流咨询 | “什么时候发货”“物流到哪了” | 根据订单状态解释当前信息 | 仅异常时 |
| 取消订单 | “我不想要了” | 仅待支付订单可申请取消 | 用户确认后创建操作记录 |
| 退款申请 | “我要退款” | 收集订单和原因，创建退款申请 | 是 |
| 退货退款 | “尺码不合适，想退货” | 收集订单、商品和原因，创建退货退款申请 | 是 |
| 质量问题 | “衣服有破损”“商品有问题” | 收集描述，优先转人工审核 | 是，高优先级 |
| 转人工/投诉 | “找客服”“投诉” | 创建人工服务工单 | 是 |
| 非售后咨询 | 闲聊、无法匹配的问题 | 礼貌说明能力范围并建议转人工 | 用户要求或连续未解决时 |

## 3. 订单状态与处理规则

| 当前订单状态 | 用户请求 | 处理规则 |
| --- | --- | --- |
| `PENDING` 待支付 | 取消订单 | 可在用户确认后取消；不创建退款申请 |
| `PENDING` 待支付 | 退款/退货 | 说明订单未支付，建议取消订单 |
| `PAID` 已支付 | 退款 | 可创建“退款申请”，状态为待人工审核 |
| `PAID` 已支付 | 退货退款 | 可创建“退货退款申请”，状态为待人工审核 |
| `SHIPPED` 已发货 | 退款/退货 | 可创建“退货退款申请”；Agent 不承诺退款成功 |
| `SHIPPED` 已发货 | 物流咨询 | 告知已发货；因当前项目未接物流接口，不编造轨迹 |
| `CANCELLED` 已取消 | 退款/退货 | 不允许重复申请，必要时转人工核验 |

所有订单查询和写操作必须验证 `order.user == request.user`。任何非本人订单一律不返回详情，也不创建工单。

## 4. 售后工单规则

### 4.1 工单类型

| 类型代码 | 名称 | 使用场景 | 默认优先级 |
| --- | --- | --- | --- |
| `REFUND` | 退款申请 | 已支付但未涉及退货的退款诉求 | 普通 |
| `RETURN_REFUND` | 退货退款申请 | 尺码不合适、买错、已发货后申请退货 | 普通 |
| `QUALITY_ISSUE` | 质量问题 | 破损、瑕疵、错发等 | 高 |
| `DELIVERY_ISSUE` | 物流异常 | 已发货但用户反馈长期未收到或状态异常 | 普通 |
| `ORDER_VERIFICATION` | 订单核验 | 订单归属、金额或状态存在异常 | 高 |
| `HUMAN_SERVICE` | 人工服务 | 用户主动要求人工、投诉或超出 Agent 能力范围 | 普通 |
| `SYSTEM_EXCEPTION` | 系统异常 | 工具连续失败、执行无法恢复 | 高 |

### 4.2 工单状态流转

```text
待用户确认 -> 待人工审核 -> 审核中 -> 待用户补充 -> 已通过 / 已拒绝 -> 已关闭
                                  \-> 用户取消
```

- “待用户确认”属于确认请求，不创建正式工单。
- 用户确认后创建正式工单，初始状态为“待人工审核”。
- 管理员可在 Django 后台改为“审核中”“待用户补充”“已通过”“已拒绝”或“已关闭”。
- Agent 只能创建工单和读取状态，不能自行将工单改为“已通过”或“已拒绝”。

## 5. 自动建工单触发条件

以下任何一项满足时，系统自动创建工单，并在回复中告知工单编号：

1. 用户确认提交退款、退货退款或取消订单申请。
2. 用户明确表达“人工”“客服”“投诉”“举报”等转人工意图。
3. 用户反馈商品破损、错发、质量问题等质量类问题。
4. Agent 连续两轮无法获得足够的订单信息，且用户仍希望继续处理。
5. 查询到订单归属、订单金额或订单状态异常。
6. 同一工具在同一会话连续执行失败两次。
7. 用户要求的事项超出已定义规则，且 Agent 无法提供可靠答案。

普通订单查询、商品咨询、售后规则解释不会自动创建工单。

## 6. 对话工作流

```text
用户消息
  -> JWT 身份校验
  -> 读取会话状态和历史摘要
  -> 意图识别
  -> 生成不超过三步的计划
  -> 调用只读工具查询订单或规则
  -> 是否需要写操作？
       -> 否：回复答案，更新会话摘要
       -> 是：生成确认卡片，等待用户确认
  -> 用户确认后调用受控写工具
  -> 在事务中创建售后工单和工具审计日志
  -> 返回工单编号与状态，更新记忆
```

退款示例：

```text
用户：这件衣服尺码不合适，我要退货。
Agent：查询用户订单，要求选择对应订单。
用户：选择订单 A。
Agent：展示申请摘要：“订单 A 将提交退货退款申请，原因：尺码不合适。”
用户：确认提交。
系统：创建 RETURN_REFUND 工单，状态为“待人工审核”。
Agent：返回工单编号和下一步说明。
```

## 7. 人工确认和权限规则

### 必须确认的操作

- 创建退款申请。
- 创建退货退款申请。
- 取消待支付订单。
- 提交包含用户主动填写的售后原因或联系信息的人工工单。

确认卡片必须展示订单号、商品、金额或申请类型、原因和即将执行的操作。确认请求有效期设为 10 分钟，过期后不能执行。

### 自动执行的只读操作

- 查询当前用户订单列表。
- 查询当前用户订单详情。
- 查询售后规则。
- 查询当前用户自己的工单进度。

### 禁止 Agent 执行的操作

- 查询或修改其他用户的数据。
- 直接修改支付金额、支付状态或向支付渠道发起真实退款。
- 执行任意 SQL、Shell、文件系统或未注册的网络请求。
- 将工单直接标记为审核通过、已退款或已拒绝。

## 8. 失败处理和回滚要求

- 所有写操作使用数据库事务；工单、确认结果和审计记录要么全部成功，要么全部回滚。
- 每个确认请求携带幂等键；同一次确认重复点击只能创建一张工单。
- 工具失败不向用户暴露内部堆栈、数据库配置或密钥。
- 同一工具连续失败两次，停止重试并创建 `SYSTEM_EXCEPTION` 工单。
- 模型输出的工具名不在白名单或参数不符合 Schema 时，直接拒绝执行并记录审计日志。

## 9. 记忆策略

| 记忆类型 | 保存内容 | 保存位置 | 禁止保存内容 |
| --- | --- | --- | --- |
| 会话短期记忆 | 当前意图、所选订单、待确认操作、最近对话摘要 | Agent 会话记录 | 密码、JWT、完整支付信息 |
| 用户长期记忆 | 语言偏好、常见售后偏好、已关闭工单摘要 | 用户记忆记录 | 完整收货地址、身份证、银行卡信息 |
| 审计记录 | 工具名、脱敏参数、执行结果、耗时、操作人 | 工具执行日志 | 密码、Token、原始密钥 |

## 10. 第一步验收标准

以下规则将作为后续自动化测试和演示的验收条件：

1. 非本人订单无法被查询或创建售后工单。
2. 待支付订单申请退款时，Agent 引导用户取消订单，而不创建退款工单。
3. 已支付订单只有在用户确认后才会创建退款申请。
4. 已发货订单申请退货时，创建退货退款工单，而不是承诺直接退款。
5. 质量问题直接创建高优先级工单。
6. 用户说“转人工”时，直接创建人工服务工单。
7. 同一确认请求重复提交，不会创建重复工单。
8. 工具连续失败两次，会创建系统异常工单并停止继续调用。
9. Agent 无法伪造物流轨迹或退款成功结果。
10. 所有写操作都有确认记录和审计日志。
