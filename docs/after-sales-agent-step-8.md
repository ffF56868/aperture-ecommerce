# 第八步：工具权限矩阵与运行时拦截

本步将售后 Agent 可用工具整理为可执行的权限矩阵。权限不只依赖模型提示词，而是在每次实际调用前由后端再次检查。

## 权限矩阵

| 工具类别 | 代表工具 | 执行专员 | 权限等级 |
| --- | --- | --- | --- |
| 订单、规则、工单查询 | `list_my_orders`、`get_my_order_detail`、`list_my_after_sales_cases` | 订单核验、规则、工单进度专员 | 只读 |
| 提交前准备 | `prepare_after_sales_confirmation` | 售后流程专员 | 必须用户确认 |
| 低风险售后工单 | `create_after_sales_case` | 售后流程专员 | 受控建单 |

确认执行、订单取消等真实写操作没有注册给模型，只能由登录用户点击确认卡后进入独立的、事务化后端接口。

## 新增拦截规则

当会话存在一张有效的“待确认”卡片时：

1. 后续模型请求只会看到只读工具。
2. 即使模型仍然伪造调用新的退款、转人工或建单工具，后端会返回 `CONFIRMATION_PENDING` 并拒绝执行。
3. 用户必须先点击“确认提交”或“取消”，才能发起新的售后写操作。

这避免了同一个会话中出现两张互相冲突的退款、退货或人工服务申请。

## 执行顺序

```text
模型请求工具
  -> 工具是否在白名单
  -> 是否属于本轮分配的专员
  -> 当前会话是否允许读/写操作
  -> 权限等级是否允许
  -> 是否存在待用户确认的申请
  -> 参数 Schema 校验、用户归属校验
  -> 执行并写入审计日志
```

任一环节不通过都会拒绝执行，并在 Django 后台“工具执行审计”中记录失败代码；不会向用户返回内部异常、数据库信息或密钥。

## 用户如何体验

正常使用方式不变：仍然在售后助手输入问题，确认卡出现后再决定“确认提交”或“取消”。当你尚未处理已有确认卡又提出新的售后申请时，系统会要求先处理当前申请，不会静默创建第二张工单。
